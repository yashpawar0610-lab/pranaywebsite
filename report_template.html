Abstract

Modern fitness facilities and gyms face operational bottlenecks stemming from manual record-keeping, disconnected membership tracking, lack of self-service booking options for members, and absent analytical tools for progress tracking. Traditional paper-based registers and basic spreadsheets lead to billing errors, double-booked workout slots, and decreased client retention.

FitZone Pro is an enterprise-grade full-stack web application architected to digitize and automate gym operations end-to-end. Built using the modern MERN stack (MongoDB, Express.js, React 18, Node.js), FitZone Pro bridges the divide between gym administration and members through an interactive, responsive portal.

Key capabilities include:

  • Role-Based Access Control (RBAC): Strict separation between Administrator and Member privileges with cryptographically secure JWT authentication and password hashing (bcryptjs).
  • Subscription & Tier Management: Automated membership lifecycles across Basic, Standard, Premium, and Elite tiers with status monitoring.
  • Live Booking Engine: Real-time session reservation with class capacity tracking, slot collision avoidance, and automated conflict rejection.
  • Fitness & Health Analytics: Integrated interactive Body Mass Index (BMI) calculator, Total Daily Energy Expenditure (TDEE) and macronutrient estimator, and visual workout metric logging powered by Recharts.
  • Comprehensive Admin Suite: Centralized dashboard providing financial KPIs, member roster management, workout program CRUD, trainer assignment, and contact inbox tracking.

System Architecture & Technology Stack

1. Architectural Paradigm

FitZone Pro follows a decoupled Three-Tier Client-Server Architecture adhering strictly to RESTful design principles. The presentation layer (Frontend) communicates with the business logic layer (Backend API) asynchronously via JSON payloads over HTTP/HTTPS.

The database layer uses MongoDB, structured with Mongoose ODM to enforce strict type checking, validations, default values, and relational references (ObjectId).

1. User Schema (`User.js`)

email String Required, Unique, Lowercase Unique user identity for authentication
password String Required, select: false Hashed password (bcrypt 12 rounds)
role String Enum: ['member', 'admin'] User authorization privilege level

membership.plan String Enum: ['Basic', 'Standard', 'Pro', 'Elite'] Current subscribed fitness tier
membership.status String Enum: ['active', 'inactive', 'expired'] Subscription standing

2. Comprehensive Viva Voce Questions & Answers

Q1: Why did you choose MongoDB over a traditional Relational Database (SQL)?
A: Gym data entities such as workout programs, trainer profiles, and member progress have dynamic, nested structures (e.g., array of schedule days, social links, progress history logs). MongoDB's flexible JSON-like document model allows rapid schema iteration without costly SQL migration scripts, while Mongoose provides strict schema validations and indexing.
Q2: How is security implemented for authentication and password protection?
A: Passwords are never stored in plaintext. They are hashed using bcryptjs with an algorithmic cost factor of 12 salt rounds before persisting to MongoDB. When logging in, the server generates a signed JSON Web Token (JWT) containing the user's ID and role encrypted with a secret key. Protected endpoints require the token in the Authorization: Bearer <token> header, validated by custom Express middleware (auth.js).
Q3: How does the system prevent double-booking or overcapacity in workout classes?
A: In bookingController.js, prior to inserting a reservation, the API executes a query checking existing confirmed bookings for that specific program and date. If the count reaches program.capacity, the system rejects the booking with an HTTP 400 error indicating the class is full.
Q4: Why is vercel.json required when deploying React on Vercel?
A: React is a Single Page Application (SPA) using HTML5 History API for routing. When a user directly visits or refreshes a URL like /dashboard, the server looks for a physical dashboard.html file which doesn't exist. The vercel.json rewrite routes all incoming requests to /index.html, letting React Router handle page rendering on the client.
